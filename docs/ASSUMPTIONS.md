## Provisional Product Decisions

Keep clear employee, compensation, analytics, infrastructure, and security responsibilities. Use controllers, services, repositories, DTOs, and straightforward mapping where needed within features. ## Approved Data Model Decisions

The user approved [DATA_MODEL.md](DATA_MODEL.md): four tables (`employees`, `departments`, `countries`, `currencies`), current salary on the employee record, controlled lookup data, required foreign keys, and no cascading lookup deletion. Department names are required, at most 100 characters, and unique without regard to case. Country and currency codes are uppercase ISO-shaped keys whose actual values require verified reference records.

Employee management owns the employee entity/repository; compensation owns monetary rules; employee application services coordinate combined updates atomically; analytics owns read-only projections. One employee version supports optimistic locking; the API requires the original browser-edit version in each full update and reports stale edits as `409`.

Employee creation and full editing use shared normalization/reference/salary validation and precise unique-constraint translation. Names are limited by Unicode code points, matching PostgreSQL character counting; null characters are rejected because PostgreSQL text cannot store them. Dedicated HTTP DTOs map typed application values to the string contract. Creation time is database-generated through Hibernate; write services set latest-change time from PostgreSQL's transaction clock. There is no salary history or individual audit attribution.

Start with primary-key/uniqueness indexes and employee indexes on `(department_id, id)` and `(country_code, id)`. Finalize other indexes against query contracts and measurements. Do not assume B-tree indexes accelerate arbitrary name substring searches. Use a unique ID as the final sort tie-breaker.

PostgreSQL's fixed-scale numeric coercion can round invalid input, so application writes and seeding must validate before persistence. Direct SQL bypassing validation may still round; no trigger-based precision machinery is planned. V1 implements the schema and explicit `NaN`/non-positive salary rejection; V2 initializes eight departments, six countries, and six currencies, with lookup names limited to 100 characters. Migration/constraint tests run against isolated PostgreSQL 18.6 databases.

Docker Compose supplies the persistent local development database with loopback binding. Credentials live in ignored local configuration, outside Git. Flyway owns initialization, validates completed migrations, and has clean disabled. Application startup requires database configuration and successful migration. Testcontainers databases are disposable and separate from development data; Failsafe runs integration tests during `verify`. Production database roles/hosting remain deployment decisions.

## Approved API Decisions

The user approved [API.md](API.md): JSON REST under `/api/v1`; integer strings for IDs/versions and decimal strings for money; server-managed timestamps in ISO 8601 UTC; full `PUT` updates with original-version checks; and an application-owned page envelope. Unknown/missing write fields and invalid references are rejected rather than silently accepted.

Use RFC 9457 Problem Details, including security-filter failures. Duplicate employee numbers and stale updates have distinct `409` codes. Login/session/logout and CSRF endpoints use API responses rather than HTML redirects. Login is URL-encoded and CSRF-protected; refresh the separate CSRF token after login/logout. Preserve stale forms and offer reload rather than silently retrying against the newest record.

Authentication/session/CSRF endpoints and security-filter errors are implemented and tested over HTTP. The account comes from external `HR_USERNAME` and raw BCrypt `HR_PASSWORD_HASH`; cost 12 is recommended and at least 10 is required. No credentials are generated or defaulted. Web startup fails on missing/malformed account settings. Password and hash values are not returned or explicitly logged. The shared account remains a demo access mechanism rather than individual identity management. Local setup is documented in the README; production HTTPS/proxy settings remain deployment work.

Employee creation is implemented through HTTP. Strict JSON rejects non-string values for its fields, unknown/server-managed fields, and trailing tokens. Controller validation/error handling returns the approved field errors, generic malformed-request errors, and duplicate conflicts; unexpected responses omit exception details. Required-field errors are ordered by field name. There are no new migrations or changes to monetary rules for this HTTP step.

Employee retrieval by ID is implemented through an authenticated GET with no CSRF header requirement. It reuses the employee response DTO and maps results inside a read-only query service transaction. Lookup labels are fetched with the employee through an entity graph. A valid missing ID returns `404 EMPLOYEE_NOT_FOUND`; malformed/nonpositive/out-of-range IDs return field validation errors. Shared positive-ID parsing accepts ASCII digits/leading zeros and rejects signs or surrounding whitespace. Reads preserve salary, version, and timestamps.

Full editing is implemented at `PUT /api/v1/employees/{id}`, requiring six editable string fields and the original nonnegative integer-string version. The service checks the original version and uses optimistic locking through commit. Effective changes advance server-managed version/update time; unchanged normalized submissions preserve metadata but can still conflict with a concurrent writer. Missing targets return `404`, stale edits `409 STALE_EMPLOYEE`, and duplicate numbers a separate `409`. Validation/conflict failures roll back the replacement. No automatic retry or upsert is performed. These behaviors were approved for this step; frontend form preservation/reload remains future UI work.

Authenticated `GET /api/v1/reference-data` is implemented with string department IDs and integer currency minor units. The response reads current supported catalogs in database order: department name/ID and country/currency code. Empty catalogs return empty arrays. The existing security policy requires a session but no CSRF token for GET. Catalog administration, caching, and pagination are excluded for these small migration-controlled tables; future live administration would need explicit consistency rules.

Basic authenticated employee pagination is implemented with optional `page`/`size`, defaults `0`/`25`, page range `0..2147483647`, and size range `1..100`. Only single ASCII-digit values are accepted; unsupported/repeated parameters return `400`. Ordering defaults to employee number/ID; the implemented sort allowlist is described below. Counts and offsets use long arithmetic, and an empty/out-of-range request returns empty items with actual totals. The service counts first, fetches only the requested in-range employees plus labels, and returns the existing employee representation in an application-owned envelope. Default read-only transaction isolation does not guarantee a snapshot across count/content or separate page requests.

Literal case-insensitive search is implemented through optional `q`: strip surrounding Unicode whitespace; absent/blank means no search; cap normalized input at 200 Unicode code points and reject null characters. Search the full literal substring of employee number OR full name with PostgreSQL case conversion. Escape LIKE metacharacters with explicit `!`, bind the same pattern to shared-predicate count/content queries, and preserve the selected ordering and matching totals. Repeated `q` is rejected. No schema/dependency/index changes were required.

Department/country/currency filters are implemented and combined with AND around the grouped search OR condition. Optional department IDs follow existing positive-Long syntax; codes share employee-write normalization. Provided filters must reference supported catalogs; blank, malformed, unknown, and repeated values return field errors. Missing filters impose no restriction. Each supplied catalog is validated before employee count/page queries, including empty/no-match cases. Country and currency remain independent. Count/content share the same parameterized condition, with an explicit text cast for a nullable search pattern.

Allowlisted sorting is implemented through optional `sort=field,direction`: the six approved fields and exact lowercase `asc`/`desc`, defaulting to `employeeNumber,asc`. Names are case-sensitive; blank, malformed, unknown, or repeated sort values return field errors. Typed values map to fixed JPA properties; ID ascending is always the final tie-breaker, including for descending primary order. Text order follows database collation. Salary sort requires an explicit supported currency filter, including when no employees match; invalid provided currencies remain currency field errors. No conversion, dependency, schema change, or new index was added.

The analytics service and grouped PostgreSQL read are implemented. A shared `EmployeeReadCriteria` and catalog validator preserve listing normalization/escaping/filter semantics; listing page/sort behavior remains separate. One grouped SQL statement produces counts, exact totals/minimums/maximums and currency metadata. Java derives currency summaries from those captured aggregate rows and rounds averages once from exact totals/counts. No cross-currency monetary result or per-employee-range cap is applied to totals. Groups order by numeric department ID or country code, then currency; summaries order by currency. A coordinated write-after-read test verifies both result levels retain the grouped read.

The analytics HTTP contract is implemented through an authenticated GET endpoint, strict parameter parsing, and dedicated string-valued money DTOs. Exact lowercase grouping names are accepted; absent grouping defaults to department. Duplicate parameters and unsupported pagination/sorting parameters are errors. HTTP tests cover response types/values, normalization, validation, empty data, and access behavior. Existing session, CSRF, and error policies are reused. Query/index measurement and production runtime verification remain later steps.

The explicit seed command is implemented: `--seed-employees` runs without an HTTP server/HR account, loads exactly 10,000 synthetic employees, then closes the application. Normal startup never seeds. Dataset version 1 fixes random seed `20261018`, country order, curated international names, and illustrative annual salary bands. Catalog IDs and currency precision are read from the database; all generated records pass shared employee/salary validation. Country/local-currency pairings are only a seed choice. Reproducibility covers business fields with unchanged code/catalog metadata on Java 21; generated IDs/timestamps may differ. One transaction with an employee-table write lock and JDBC batches of 500 rejects nonempty tables, preserves HR edits on rerun, serializes concurrent seeds, and rolls back partial failures. No reset/overwrite mode, migration, dependency, or general import workflow is added. Isolated tests cover loading and listing/analytics at 10,000 rows; these do not establish latency targets.

## Future Expansion and Trade-offs

- Current-value editing keeps the first model small but provides no salary history or audit trail. History would require effective dates and additional persistence rules.
- Separate-currency reporting preserves correctness but cannot produce a single organization-wide monetary total. Conversion would require rates, effective dates, and rounding policy.
- Single-account session login supports the demo but provides no individual attribution. In-memory sessions are lost on restart; multiple instances would require a session strategy. Multiple roles would require an explicit authorization model and tests.
- Database pagination and aggregation support the current dataset. Larger-scale readiness must be measured; do not claim support for 100,000 or one million employees without evidence.
- CSV workflows would need validation, duplicate handling, and failure semantics. Payroll and approval workflows would require separately agreed business rules.
